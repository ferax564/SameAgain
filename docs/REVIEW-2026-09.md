# Same Again: application review (September 2026)

This review covers commit `1c7e091`. It combines four things:

- **Build and test run:** typecheck, the unit suites, lint and a production build.
- **Browser testing:** end-to-end runs with Playwright/Chromium against a local `vite` dev server. The local server used a D1 database with the migrations applied, plus the spoofed dispatcher identity headers, to act as users Alice, Bob, Carol and Dave.
- **Accessibility scan:** axe-core.
- **Code review:** server and security, client sync and domain logic, and frontend and tooling.

Each finding is tagged:

- **[Tested]**: reproduced in the running app or with the API.
- **[Verified]**: reproduced by running the pure functions in isolation.
- **[Code]**: found by reading the code. **(plausible)** means it could not be confirmed.

---

## 1. Summary

The product is well designed. Several things work correctly, and the browser tests confirmed them:

- Invitation security.
- Optimistic concurrency and conflict review.
- Idempotent operation replay.
- Private photo handling.
- The demo mode, desktop layout and mobile layout, which are polished.

The main weaknesses are:

1. **Sync reliability.** Several ordinary situations stop all syncing:
   - finishing a normal-sized trip;
   - a malformed request;
   - an expired session;
   - a stalled request;
   - two open tabs.
2. **Scalability and cost.** Every 4 seconds the app polls for the whole household dataset, and there are no indexes, pruning or visibility check.
3. **Hardening:**
   - Identity comes only from headers.
   - There is no CSP or frame protection.
   - Input errors come back as 503.
   - Rate limits shared by all users can be exhausted by one person.
4. **Maintainability.** The source is formatted like minified code: one 82 KB component with 32 `useState`s. Lint fails, there is no CI and no UI or E2E tests, and there are 12 unused dependencies and 46 unused UI components.

## 2. Critical and high-priority issues

### H1. Finishing a normal shopping trip is rejected, and all syncing then stops [Tested]
- **What happens:** the client puts a full copy of every purchased item, including its embedded product, into the `trip` record:
  - the client side is `app/same-again.tsx:79`: `items:done.map(i=>({...i.data,originalItem,originalVersion}))`;
  - the server's `validate()` caps every non-recipe record at 40,000 characters (`app/api/data/route.ts:13`).
- **Reproduced:** 20 product-linked items made a 38.9 KB trip, which was accepted. 25 items made 49 KB, which returned `400 This record is too large.` Real Open Food Facts products are larger than the samples, so the limit is reached at roughly 12–20 items.
- **Impact:** `lib/use-household.ts:17` treats a 4xx as a final rejection and sets `blocked=true`. Every later change stays queued until the user discards the trip.
- **The copies are unnecessary:** the server rebuilds `d.items` from the database anyway (`route.ts:37`).
- **Fix:** send only `{originalItem, originalVersion}` per item, and check size after the server has rebuilt the items. Templates have the same risk.

### H2. Input errors are reported as 503, so the client retries them forever [Tested]
- **Cause:** `lib/server.ts:14` maps any error without a `.status` to `503 "Your changes have been kept for retry"`.
- **Reproduced:**
  - malformed JSON returns 503;
  - `{"action":"settings"}` without `settings` returns 503 (`JSON.stringify(undefined).length` throws);
  - `/api/catalogue?country=constructor` returns 503 (see M8).
- **Impact:** the outbox retries 5xx responses indefinitely with backoff, so one bad queued operation holds up every operation behind it.
- **Fix:** map `SyntaxError`, `ZodError` and `TypeError` raised while handling input to 400. Check types before using values.

### H3. Polling every 4 seconds re-downloads and re-renders everything [Tested + Code]
- **Tested:** about 3 `GET /api/data` requests per 12 seconds while idle.
- **Code (`lib/use-household.ts:12,20`, `route.ts:14`):** each poll does all of the following.
  - Returns *every* record, including soft-deleted rows, which are never purged. Trips hold full product copies and meals hold full recipe copies.
  - Keeps running while the tab is hidden, and never backs off after 401, 403 or errors.
  - Starts even if the previous poll hasn't finished.
  - Calls `setRecords` with a new array every time, which re-renders the whole 82 KB component tree. The app uses no `useMemo`, `useCallback` or `memo` anywhere.
  - `JSON.stringify`s the whole dataset into localStorage. Once the roughly 5 MB quota is reached, the "storage full" toast appears every 4 seconds.
- **Server cost:** every request also performs two D1 writes, the `users` upsert and the rate-limit upsert.
- **Fix:**
  - pause polling while `document.hidden`;
  - allow only one request in flight at a time;
  - back off after errors;
  - add a household revision counter with ETag/304, or an `updated > ?` delta;
  - skip `setState` and `persist` when nothing has changed;
  - purge old tombstones and operation receipts.

### H4. Two tabs overwrite each other's offline queue [Code]
- **Cause:** `use-household.ts:10` saves `{records, queue}` under one localStorage key and reads it only when the hook mounts. Nothing listens for `storage` events and nothing coordinates between tabs.
- **Scenario:** tab A's queued "Milk" is overwritten by tab B's "Eggs". When tab A is then closed, "Milk" is lost.
- **Fix:** store one IndexedDB entry per operation, or elect a single sending tab with Web Locks and BroadcastChannel.

### H5. Identity is trusted from request headers alone (deployment-dependent) [Tested]
- **Cause:** `lib/server.ts:9` and `app/chatgpt-auth.ts:21` read `oai-authenticated-user-id` and `-email` directly from the request, with no signature or secret.
- **Tested:** all of the local E2E tests signed users in just by setting these headers.
- **Risk:** this is safe only if every path to the Worker goes through the trusted dispatcher. If the Worker is reachable directly (a `*.workers.dev` route, a preview URL, or a proxy that forwards client headers), anyone can impersonate any user, delete households and claim invitations.
- **Fix:** have the dispatcher sign an assertion (HMAC or JWT) that the Worker checks against a secret binding. Strip `oai-authenticated-*` headers otherwise, and disable `workers_dev` and preview routes.

### H6. A stalled request stops syncing until the page is reloaded [Code]
- **Cause:** `api()` (`use-household.ts:7`) sets no timeout, and `working.current` stays `true` until the request settles.
- **Scenario:** in a shop with weak signal, a request hangs. Every later flush, including the one triggered by the `online` event, returns early.
- **Fix:** use `AbortSignal.timeout(15000)` and treat a timeout as a temporary failure.

## 3. Medium-priority issues

### Sync and client state
- **M1. A retried update conflicts with itself** [Code]
  - When `UPDATE … WHERE version=?` changes 0 rows, the server returns 409 without checking whether that operation id already has a receipt (`route.ts:47`). Creates are handled correctly.
  - A retry after a dropped response, or two tabs flushing at once, therefore shows the "Two shoppers" dialog for the user's own change.
- **M2. Undoing a change that cancels out still raises a conflict** [Tested]
  - Bob checked and then unchecked an item while offline. Meanwhile Alice checked it. When Bob came back online he got a conflict, although his net change was nothing.
  - During the conflict the sync badge said "Sync failed", which is misleading.
  - Undo toasts and "Combine quantities" also send the stale `version` they captured (`mutate` trusts `old.version`).
- **M3. Other members' changes stop arriving while anything is queued** [Code]
  - `refresh` returns early whenever the queue is not empty, so during a long offline period or a blocked queue the user sees a stale list with no warning.
- **M4. An expired session (401) is shown as a rejected change** [Code]
  - The UI shows a "rejected draft" with a Discard button that also fails. No re-authentication prompt appears.
- **M5. The last household used is not remembered** [Code]
  - The app always boots into `households[0]`. Changes queued for another household stay stranded.
  - "Sign out & clear device cache" checks pending changes only for the current household before deleting every `same-again:*` key.
- **M6. The offline fallback requires `navigator.onLine === false`** [Code]
  - A captive portal, a connection with no internet, or a server 5xx shows an error instead of the cached list.
- **M7. Long names show an unfriendly error** [Tested]
  - A 300-character quick-add is accepted by the client (the input has no `maxlength`) and rejected by the server (160-character limit).
  - The error banner then shows the full 300 characters and "…is required..", with a doubled period.

### Server and security
- **M8. Country and retailer lookups accept prototype keys** [Tested]
  - `countries['constructor']` is truthy, so `country:'constructor'` is saved in settings and records, and the catalogue endpoint crashes with a 503.
  - **Fix:** use `Object.hasOwn`, or a `z.enum` of the keys.
- **M9. Security headers are missing** [Tested]
  - Only `nosniff` and `Referrer-Policy` are sent.
  - There is no `Content-Security-Policy`, `frame-ancestors` / `X-Frame-Options`, `Permissions-Policy` (the app uses the camera and geolocation) or HSTS.
  - Without frame protection, delete, transfer and invite actions can be clickjacked.
- **M10. Invitations keep working after their creator loses authority** [Code]
  - `join` does not check that `created_by` is still an owner or admin.
  - Removing or demoting an admin, or deleting their account, does not revoke their invitations.
  - A removed admin who kept an unbound token can rejoin.
- **M11. Catalogue queries can read whole tables** [Code]
  - A `retailer` with an empty `q` becomes `WHERE 1=1` (`lib/catalogue-cache-search.ts:14`), and the substitution fallback runs `SELECT data FROM catalogue` with no `LIMIT`.
  - Every OFF search adds rows, so the table only grows.
- **M12. Shared rate limits can be exhausted by one user** [Code]
  - Photon allows 12 requests/minute and 300/day globally, while each user may make 8/minute. One user can use up the daily store-search quota for everyone in about 40 minutes.
  - The OFF global 60-second cooldown starts after *any* failure.
- **M13. Missing indexes** [Code]
  - `memberships(user)` is queried on every GET, but the primary key is `(household,user)`.
  - `invitations(household)` and `operations(user|household)` have no index.
  - Barcode lookup uses `json_extract(data,'$.barcode')` across the whole `catalogue` table.
  - `deleteAccount` runs `data LIKE '%uid%'` across every household.
- **M14. Tables grow without limit** [Code]
  - `operations` receipts (up to about 120 KB each), `limits` rows, expired `cache` rows and tombstones are never pruned. Add a scheduled cleanup.
- **M15. Account deletion leaves personal data behind** [Code]
  - `invitations.recipient_email`, `created_by` and `used_by` remain.
  - User ids remain inside other users' `operations.result` JSON and in `limits` keys.
  - The version-guarded anonymisation `UPDATE`s silently skip records that change at the same moment.
- **M16. A race can leave a household with no owner** [Code]
  - The `role`, `leave` and `remove` statements lack `AND role!='owner'`, so a transfer that runs at the same time as the new owner leaving leaves the household ownerless.
- **M17. Profile names are never refreshed** [Tested]
  - `INSERT … ON CONFLICT DO NOTHING` (`lib/server.ts:9`) stores the display name and email only at first sign-in, so the UI kept showing "alice@example.com" and "Bought by alice@example.com" after a full name became available.
  - **Fix:** use `DO UPDATE SET name=excluded.name, email=excluded.email`, and only when they have changed.

### Domain logic
- **M18. Receipt parser errors** [Verified]
  - A whole-number price is read as the quantity: `Olive oil 12.00 12.00` gives quantity 12, and the row is pre-selected. Italian VAT-letter rows (`OLIO EVO 10,00 A`) do the same.
  - Thousands separators break parsing: `TOTAL EUR 1.234,56` gives a total of 4.56.
  - HUF and ISK receipts, which have no decimals, give 0 items even though both currencies are supported.
- **M19. Quick-add does not parse quantity or unit, and does not detect duplicates** [Tested]
  - `2 kg apples`, `bread x3`, `500g pasta` and `eggs 12` were all saved as "1 pieces" with the text as the name.
  - `milk` and `Milk` were both added without a duplicate warning.
  - Everything was filed under "Other".

### Frontend
- **M20. There is no error boundary** [Code]
  - `app/` has no `error.tsx` or `global-error.tsx`, so one render exception blanks the whole app.
- **M21. The theme flashes and ignores the OS setting** [Code]
  - The theme is read from localStorage in `useEffect`, so the page always paints light first. `prefers-color-scheme` and `color-scheme` are not used.
  - Toasts use `next-themes` without a provider, so they follow the OS setting rather than the app's toggle.
- **M22. Accessibility** [Tested]
  - axe reports:
    - **78 contrast failures** on a populated list; completed-item text is 2.63:1.
    - `aria-label` on a plain `<span>` in the photo fallback (`app/ui.tsx:10`), which needs `role="img"`.
  - The code also shows:
    - 33 font sizes of 11 px or smaller, including 9 px eyebrows;
    - input borders at 1.35:1;
    - a 15 px mobile input that triggers iOS zoom on focus;
    - touch targets smaller than 44 px (`.iconbtn` is 30 px, `.item-more` is 28 px);
    - the conflict dialog's ✕ and Escape silently do nothing.
- **M23. The language setting does nothing** [Tested]
  - The UI offers en/it/fr/de/es, "saved for future localisation", but every string is hardcoded English and `<html lang="en">` is fixed.
  - Number formats use `'en'` while dates use the browser locale, so formats are mixed.
  - Hide the setting or implement i18n.
- **M24. The landing page loads images from a third party** [Tested]
  - The signed-out landing page loads three product photos directly from `images.openfoodfacts.org`, which shares visitor IPs with OFF.
  - When that host was unreachable, the page showed "Photo unavailable" and never reached network-idle.
  - Serve local copies instead.

## 4. Low-priority issues

- **Barcodes** [Verified]
  - The "local / variable-weight" check tests the raw code, so UPC-A `025000044786` is flagged as local. In-store EAN-13 codes starting `04` are missed.
  - UPC-E is not in the scanner formats, and 8-digit codes are always treated as EAN-8. Real UPC-E `04252614` is rejected.
- **Pack sizes:** `pack("1.000 g")` returns 1 g; `75 cl` and `6 x 330 ml` return null. `totals` multiplies a price per unit by the quantity in grams, so 500 g at 2.50 comes to 1,250.
- **Conflict resolution**
  - Resolving a conflict on a deleted record recreates it under a *new* id, which leaves child records orphaned.
  - Resolving drops any edits made while the dialog was open.
- **Operations the server applies that the client never mirrors:** finishing a trip deletes its items, and a list currency change updates its items. Later edits to those items get a 409.
- **Unguarded storage calls:** `JSON.parse` of the cache and `localStorage.setItem` are unguarded, so a corrupt cache crashes the app on boot.
- **Service worker:** the fixed cache name `same-again-shell-v3` means old hashed assets are never evicted. OCR model files are not cached offline.
- **CSRF defence in depth:** when `Origin` is absent, the check passes (`lib/server.ts:13`), and `/api/data` accepts `text/plain` bodies [Tested]. Require `Origin` or `Sec-Fetch-Site`, plus `application/json`.
- **Loose record schemas:** `.passthrough()` on record schemas stores arbitrary extra fields. `addedBy`, `reportedBy` and `purchasedBy` can be forged on favourite, template and observation records. `language` is not validated.
- **Photos:**
  - there is no per-household quota;
  - photos are not deleted when their record is deleted;
  - EXIF is stripped only on the client, so a direct API upload keeps GPS data.
- **Invitations:** an existing member can use up an invitation. Tokens are in the query string (`?invite=`) and stay in the URL and browser history after a failed join [Tested].
- **Worker cache headers:** the Worker forces `no-store` on all `/api/*` responses, which overrides the intended caching on `/api/demo-catalogue`. That endpoint needs no sign-in, has no rate limit, and ranks a 9.8 MB index in memory on every call.
- **Status badge before sign-in:** the sync badge says "Synced" before sign-in and while loading [Tested].

## 6. What works well

- **Invitations** [Tested]
  - A sign-in with the wrong email is refused with 403.
  - A second use is refused with 410.
  - Tokens have about 244 bits of entropy and only their SHA-256 hash is stored.
  - Single use is enforced atomically in a D1 batch.
- **Access control:** a membership check runs on every household-scoped path, and admin and owner roles are separated correctly.
- **Concurrency:** version-based updates with atomic idempotency receipts. A conflicting offline edit correctly opens a side-by-side review dialog [Tested]. Changes reached another member in about 2.4 seconds [Tested].
- **Output escaping and CSRF** [Tested]:
  - An HTML payload in the household name was rendered as text.
  - A cross-origin POST was rejected with 403.
- **Photos:**
  - the server generates the R2 keys;
  - reads are authorised by key prefix;
  - JPEG/PNG signatures are checked, so SVG is excluded;
  - size is capped while streaming;
  - responses are sent `private,no-store`.
- **SQL and SSRF:** all SQL is parameterised with LIKE wildcards escaped, and outbound hosts are fixed, so there is no SSRF path.
- **Lazy loading:** heavy libraries (zxing, tesseract, `@noble/hashes`) are loaded on demand.
- **Service worker:** it never caches `/api/` or auth routes, and it has tests.
- **UI:**
  - The mobile and desktop layouts are polished.
  - The demo is fully isolated.
  - Every icon-only button has an `aria-label`.
  - A global `prefers-reduced-motion` reset is in place.

## 7. Recommended order of work

1. **Sync reliability.** Send trip items as references only (H1). Map input errors to 400 (H2). Add a request timeout (H6). Handle 401 separately (M4). Check receipts before returning 409 (M1).
2. **Hardening.** Add a signed dispatcher assertion (H5). Add CSP, frame-ancestors and Permissions-Policy headers (M9). Use `Object.hasOwn` for lookups (M8). Revoke invitations when their creator loses authority (M10). Add `LIMIT` and required search terms (M11). Set per-user limits below the global ones (M12).
3. **Polling cost.** Pause while hidden, allow one request at a time, use a revision/ETag or delta, skip unchanged state (H3). Add indexes (M13) and a cleanup cron (M14).
4. **Tooling.** One Prettier commit, recorded in `.git-blame-ignore-revs`. Fix the lint ignores and the real lint errors. Add CI that runs typecheck, lint, test and build.
5. **Remove dead code.** Delete the 46 unused components and the 12 unused dependencies.
6. **Refactor.** Split `same-again.tsx` into view, modal and hook modules, and type `RecordData` as a discriminated union.
7. **Tests.** Add Playwright and axe smoke tests: onboarding, invite and join, add/check, offline replay, conflict, and a trip with more than 25 items. Add unit tests for `useHousehold`.
8. **UX and accessibility.** Fix contrast, set inputs to at least 16 px and touch targets to at least 44 px, add an error boundary, fix the theme flash, parse quantities in quick-add, warn about duplicates, and hide or implement the language setting.
9. **Assets.** Resize the 3.4 MB recipe photo. Move the large data files out of Git or out of the Worker bundle. Add PNG and maskable icons to the PWA manifest.
